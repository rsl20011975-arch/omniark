## 1. 최종 목표와 비목표

OMNIARK 개발자 노트를 실제 개발 경험과 실험에 근거한 기술 지식 아카이브로 성장시킨다. 결과물은 다음 네 가지를 함께 지향한다.

1. 실제 경험과 시행착오에 근거한 신뢰도 높은 콘텐츠
2. Google·네이버의 자연 검색에서 발견 가능한 원본 정보
3. ChatGPT, Claude, Gemini, Perplexity와 Google AI 검색이 참고할 만한 명료한 1차 기록
4. 애드센스 재심사 준비과 OMNIARK 프로그램·서비스 인지도의 장기적 기반

다음은 하지 않는다.

- 검색량이나 30편이라는 목표를 채우기 위한 가상 경험·중복 글·키워드 반복
- AI 인용, 검색 순위, 애드센스 승인을 약속하는 설계
- 이미 작동하는 Revenue Forge·영상·CMS 시스템을 근거 없이 다시 만드는 일
- 공개 범위가 정해지지 않은 개인사, 건강·가족 정보, 인증 정보, 미공개 사업 수치를 노출하는 일

## 2. 운영자 관점과 공개 범위

운영자는 약 8개월간 바이브 코딩으로 홈페이지, 웹서비스, 콘텐츠 자동화, 영상 제작, 수익화 도구와 자체 프로그램을 확장해 온 초보 개발자다. 콘텐츠는 코딩 전문가의 성공담을 흉내 내지 않는다. 모르는 상태에서 시작해 실제로 했던 판단, 오류, 수정, 현재 한계를 정직하게 보여 준다.

건강·가족 생활 등 개인적 배경은 운영자가 공개를 승인한 범위에서만 다룬다. 에이전트가 사후에 얻은 기술 지식은 운영자의 당시 경험으로 바꾸지 않는다.

## 3. 사건에서 검색 가능한 글로 가는 순서

```text
실제 사건 → 사건 카드와 근거 → 독자의 질문·검색 의도 조사
          → 차별화 가능성 판단 → 초안·시각 자료 → Studio 검토
          → 명시적 공개 승인 → 배포 검증 → 성과 관찰·업데이트
```

검색 수요는 사건 후보의 우선순위를 돕는 정보이지 글감의 출발점이 아니다. 각 후보에는 다음을 기록한다.

| 항목 | 기록할 내용 |
|---|---|
| 사건 근거 | 프로젝트·Git·로그·화면·대화·테스트·결과물의 위치 |
| 독자 질문 | 글이 실제로 답할 하나 이상의 질문 |
| 검색 의도 | 문제 해결, 비교, 개념 이해, 구매·이용 판단 중 무엇인지 |
| 수요 근거 | 사용 도구, 조회 날짜, 확인 가능한 수치 또는 ‘수치 미확인’ |
| 차별화 | 일반 글에 없는 실제 선택·실패·측정·한계 |
| 위험 | 개인정보·보안·미공개 사업정보·근거 부족 |
| 후속성 | 업데이트 조건, 관련 글, 다른 독자 질문 |

### 조사할 수 있는 수요 자료

- Google Search Console, Google Trends, Keyword Planner
- 네이버 검색광고 키워드 도구, 네이버 데이터랩, 네이버 서치어드바이저
- 실제 Google·네이버 검색 결과와 공식 문서

수치를 확인할 수 없으면 추정치처럼 쓰지 않는다. 검색량이 작아도 실제 문제를 해결하려는 독자가 분명한 롱테일 질문은 우선할 수 있다.

## 4. 사이트 기술·답변형 AI 발견성 점검

공개 변경 없이 다음을 먼저 실측한다. 결과는 ‘확인됨’, ‘미확인’, ‘문제’, ‘변경하려면 승인 필요’로 구분한다.

| 점검 영역 | 실제 확인 항목 |
|---|---|
| 색인 경로 | `robots.txt`, `sitemap.xml`, HTTP 상태, canonical, `noindex`, 리디렉션 |
| 본문 접근성 | 서버 응답 HTML의 제목·설명·본문, JavaScript 의존, 이미지 대체 텍스트 |
| 공유·구조화 | OG/Twitter 메타, 공개 본문과 일치하는 구조화 데이터, 글·가이드의 유형 |
| 탐색 | 모바일 읽기, 내부 링크, 관련 글, 고아 페이지, 제품·서비스 연결 |
| 크롤러 정책 | Googlebot, OAI-SearchBot 등 검색 크롤러와 학습 크롤러 정책의 구분 |
| 운영 품질 | 개인정보·연락 경로·제품 공개 상태·미완성 페이지·광고 정책 |

`llms.txt`는 표준화된 인용 보장 장치로 취급하지 않는다. 도입은 공식 자료와 실제 필요를 확인한 뒤 별도 제안으로만 다룬다. 크롤러 허용·차단 정책 변경과 사이트 전역 메타 변경은 운영자 승인이 필요하다.

## 5. 글 단위의 SEO·AEO·GEO 준비

SEO, AEO, GEO는 별도의 마케팅 문구가 아니라 독자가 질문과 답의 범위를 빠르게 이해하도록 돕는 편집 결과다.

- 제목은 한 가지 실제 질문 또는 사건을 드러낸다.
- 도입은 무엇이 있었고, 이 글이 무엇을 확인했으며, 어디까지 답하는지 말한다.
- H2는 질문·원인·해결·검증처럼 독립적으로 읽히는 문장으로 쓴다.
- 비교·해결 글에는 날짜, 버전, 조건, 실측 결과, 한계, 재현 범위를 넣는다.
- 외부 사실은 가능하면 공식 문서로 연결하고, 운영 경험·실험 결과·외부 사실을 구분한다.
- 관련 글 2~4편은 실제 독자의 다음 질문으로 이어질 때만 연결한다.
- 설명, canonical, OG, 구조화 데이터, 사이트맵은 사이트 공용 구현으로 생성한다. 글 안에 임의 스크립트나 JSON-LD를 넣지 않는다.

## 6. AI 모델 비교 실험 프로토콜

모델 추천은 사용 감상과 실험 결과를 분리한다. 현재의 가설은 다음과 같다.

- 높은 품질의 설계·결과물: Sol, Claude Opus
- 장시간 반복 테스트와 코드 수리: Terra Extra High
- 반복 코드 수정: Claude Sonnet High 또는 Extra High

이는 검증 전의 운영 경험이며 보편적 결론이 아니다. 비교 글을 제작할 때는 아래를 따른다.

1. 공식 문서에서 현재 모델명, 추론 설정, 가격, 한도, 확인 날짜를 기록한다.
2. 같은 복제 프로젝트·지시문·도구 권한·완료 조건을 사용한다.
3. 운영 프로젝트가 아닌 격리 환경에서 실행한다.
4. 완료 여부, 코드 변경, 테스트, 실제 사용, 시간, 토큰·비용, 재시도·수정 횟수를 각각 남긴다.
5. 단일 사례로 일반적 우열을 단정하지 않고, 운영자의 주관적 체감은 별도 표기한다.

## 7. 시각 자료와 증거 사용 우선순위

실제 오류 화면, 테스트 결과, 제작 결과, 전후 비교가 있으면 AI 생성 분위기 이미지보다 먼저 쓴다. 재구성 그래픽은 실제 화면처럼 보이게 하지 않고 ‘기록을 바탕으로 재구성’이라고 표시한다.

글의 긴장과 이해를 위해 증거·설명·실행 자료를 조합한다. 예시는 오류 문구를 식별정보 없이 보여 주는 화면, 코드 작성에서 실제 사용 검증까지의 흐름도, 독자가 AI에게 요청할 수 있는 완료 검증 카드다. 다크 네이비 기반의 브랜드 감각은 유지하되 카드·HUD·모션을 장식처럼 반복하지 않는다.

## 8. 애드센스 재심사 준비

초기 30편은 품질 기반을 위한 내부 목표이며, 60편 이상으로 성장하더라도 중복·빈 글을 만들지 않는다. 재심사 전에는 글 수 외에 다음을 함께 확인한다.

- 실제 경험과 근거, 완성된 공개 페이지, 탐색 구조, 모바일 접근성
- About·연락·개인정보처리방침, 공개 제품과 개발 중 제품의 구분
- 중복·빈약·미완성 페이지와 내부 연결
- 검색 색인 상태 및 광고 정책 준수

계정의 현재 사실과 재심사 여부는 `ADSENSE_STATUS.md`를 우선하며, 재신청은 운영자의 결정이다.

## 9. 발행 후 성과 관찰과 업데이트

발행 뒤에는 데이터가 쌓인 글부터 다음을 점검한다.

- 검색 노출·클릭·클릭률, 검색어, 글별 방문 추이
- 네이버 유입, 내부 관련 글 이동, 제품·서비스·다운로드 경로 이동
- 확인 가능한 추천 유입 파라미터(예: `utm_source=chatgpt.com`)
- 모델 정보·가격·한도처럼 시간이 지나 바뀐 사실

AI가 어느 답변에서 어떤 글을 인용했는지, 모든 AI 유입이 어디서 왔는지는 완전히 측정할 수 없다. 측정할 수 없는 값을 성공 지표로 만들지 않는다. 데이터가 쌓이면 제목·도입·관련 글·업데이트를 개선하되, 순위만을 위해 사실 범위를 넓히지 않는다.

## 10. 수익화 실험과 자격 게이트

OMNIARK는 수익화를 중요한 실험 주제로 다루되, ‘AI가 만들었으니 자동 수익이 난다’는 약속을 하지 않는다. 수익화 콘텐츠는 실제 실험 결과뿐 아니라 그 결과가 나오기 전 반드시 통과해야 하는 조건을 지식으로 남긴다.

| 수익 경로 | 먼저 확인할 조건 | 기록할 실제 지표 |
|---|---|---|
| 광고 | 사이트 품질·정책·심사·트래픽·광고 배치·개인정보·동의 | 심사 상태, 정책 상태, 실제 광고 노출·수익 여부 |
| 제휴 마케팅 | 각 프로그램의 가입·승인·표시 의무·링크 정책·전환 조건 | 승인 상태, 클릭·전환·취소, 수수료 지급 여부 |
| 소프트웨어·디지털 상품 | 라이선스·결제·세금·환불·지원·보안·저작권 | 다운로드·구매·환불·지원 부담, 실제 비용 |
| 유료 웹서비스 | 제공 가치·약관·결제·개인정보·운영 안정성·고객 지원 | 가입·활성 사용·유지·이탈·운영 비용 |
| 제작·컨설팅 | 포트폴리오·계약 범위·납기·권리·비밀유지·지원 범위 | 문의·계약·재작업·시간당 비용·수금 여부 |

표는 수익 경로의 일반적인 점검 틀이다. 국가, 지역, 플랫폼, 운영 주체에 따라 실제 자격과 의무가 달라지므로, 특정 서비스의 정책·수수료·세금·사업자 요건은 발행 전 공식 자료와 확인 날짜를 별도로 기록한다.

수익화 사건 카드는 다음 네 칸을 반드시 분리한다.

1. **가능성**: 어떤 방식으로 수익이 생길 수 있는가.
2. **자격·조건**: 시작 또는 지급 전 통과해야 하는 심사·정책·법적·운영 조건은 무엇인가.
3. **실제 시도**: OMNIARK가 언제 어디까지 했는가.
4. **검증 결과**: 실제 수익·비용·전환·정산이 확인됐는가, 아니면 아직 가설 단계인가.

수익 0원, 미승인, 전환 미확인, 비용만 발생한 결과도 숨기지 않는다. 개인별 세무·법률·계약 판단은 정보 제공 범위를 넘지 않으며, 필요할 때는 공식 기관 또는 자격 있는 전문가 확인이 필요하다고 명시한다.

## 11. 기존 시스템 조사와 재사용 순서

조사 우선순위는 다음과 같다.

1. omniark.co, About·제품·가이드·개발 노트의 현재 구조
2. Revenue Forge 콘텐츠 OS와 Omniark Studio의 초안·공개 경계
3. Work 홍보영상 자동 제작·예약 발행의 검증된 단계
4. One Pass Cut, Omniark Local MCP, Klang Guide, OmniPDF·OmniPlayer·OmniZip과 그 기록
5. Git, 테스트 로그, 오류 기록, 이미지·영상, 접근 가능한 작업 대화

각 시스템은 실제 작동 여부, 재사용 가능 기능, 누락 기능, 연결 비용, 보안·공개 위험으로 평가한다. 기존 자동화의 삭제·재구축·자동 공개 전환은 별도 승인 없이는 하지 않는다.

## 13. 승인 경계와 보고

조사, 사건 카드, 수요 조사, 초안, 비공개 시각 자료, Studio 초안, 로컬·격리 환경 검증은 자율적으로 진행한다. 새 글 공개, 기존 공개 글 교체·삭제, 배포, 예약·자동 발행, 크롤러 정책 변경, 공개 범위가 불명확한 정보는 명시적 승인이 필요하다.

보고는 항상 다음 세 가지를 분리한다.

- 한 것: 실제 파일, URL, 테스트, 화면, 데이터 등 확인 가능한 결과
- 못 한 것과 이유: 근거 부족, 접근 권한, 원본 부재, 승인 대기
- 다음 한 수: 운영자의 판단이 필요한 한 가지 또는 계속 진행할 다음 작업
