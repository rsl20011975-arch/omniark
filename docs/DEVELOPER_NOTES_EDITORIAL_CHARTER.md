# OMNIARK Developer Notes 기본 작업지시서

상태: 기준 문서  
적용 범위: OMNIARK 개발자 노트, 관련 Studio 편집 기능, 시각 자료, 검색 구조, 발행 대기 절차  
최종 갱신: 2026-10-15

## 1. 한 문장 목표

OMNIARK가 실제로 프로그램·웹서비스·콘텐츠 자동화·수익화 시스템을 만들며 겪은 사건을, 초급·중급·고급 바이브 코더가 다시 같은 문제를 만났을 때 길을 찾을 수 있는 지식으로 바꾼다.

목표는 글의 수가 아니다. 실제 경험에서만 나올 수 있는 판단, 실패, 수정 과정, 검증 방법을 충분한 양과 품질로 축적하는 것이다. 검색엔진과 답변형 AI에서의 발견 가능성은 이 원본 지식이 독자에게 닿게 하는 수단이며, 인용·순위·애드센스 승인을 보장하는 약속으로 취급하지 않는다.

## 2. 이 기준이 생긴 이유

지금까지의 대화에서 같은 요구가 반복됐다.

- 짧고 무난한 AI 글이 아니라, 지난 개발 과정의 구체적인 사건을 남긴다.
- 멋진 성공담보다 목표에서 벗어난 순간, 잘못된 선택, 고장, 재작업을 숨기지 않는다.
- 가능하면 해결된 사건을 우선해 독자가 따라갈 길을 보여 준다.
- 해결되지 않은 사건도 버리지 않는다. 다만 실제 기록과 일반적인 진단 지식을 분리하고, 해결됐다고 꾸미지 않는다.
- 글쓴이의 진솔한 경험을 지나치게 매끈한 홍보문으로 바꾸지 않는다.
- 초보자에게는 쉬운 설명을, 중급자에게는 구조와 원인을, 고급자에게는 검증 경계와 재발 방지 기준을 제공한다.
- 텍스트 벽을 만들지 않는다. 증거, 구조, 비교, 실천 항목을 시각적으로 이해하게 한다.
- 사이트는 다크한 정체성을 유지하되 검고 답답한 카드만 반복하지 않는다. 색은 의미를 구분하는 데 쓴다.
- 초안은 Studio에서 사람이 확인한 뒤 발행한다. 자동 공개와 무단 수정은 하지 않는다.

이 문서는 위 합의를 다음 세션과 다른 작업 도구가 다시 추측하지 않도록 고정한 기준이다.

## 3. 편집자의 역할

이 작업을 맡은 에이전트는 한 가지 역할만 수행하지 않는다.

- 편집장: 어떤 사건이 한 편의 글이 될 가치가 있는지 판단한다.
- 기록 조사자: Git 기록, 문서, 오류 로그, 테스트, 제작 결과, 대화를 대조한다.
- 기술 교사: 초보자가 모르는 개념을 실제 사건 안에서 단계적으로 가르친다.
- 기술 검증자: “작성됨”, “테스트 통과”, “실제로 사용 가능”을 구분한다.
- 시각 감독: 장식이 아니라 이해를 돕는 증거 화면, 구조도, 비교표, 검증 카드를 설계한다.
- 검색 편집자: 검색엔진과 답변형 AI가 글의 질문·답·근거·시점을 분명히 읽도록 구조화한다.

작성자는 OMNIARK 운영자다. 에이전트가 새로 알아낸 기술 지식을 운영자가 당시 알고 있었던 경험처럼 1인칭으로 꾸미면 안 된다. 실제 경험은 “제가 겪은 일”로, 사후 기술 설명은 “이 사건을 기술적으로 풀어보면”처럼 구분한다.

## 4. 독자와 난이도

모든 글은 한 사람에게 모든 것을 한꺼번에 가르치려 하지 않는다. 대신 한 글 안에 세 층을 만든다.

### 초급 독자

- 전문용어를 몰라도 사건의 목표와 문제가 이해된다.
- 어려운 용어는 처음 등장할 때 일상적인 말로 먼저 설명한다.
- 독자가 바로 복사해 쓸 질문이나 확인 목록을 제공한다.

### 중급 독자

- 문제가 어느 계층에서 발생했는지 알 수 있다.
- 코드 작성, 개별 기능, 시스템 연결, 실제 사용 검증의 차이를 이해한다.
- 다음 프로젝트에서 같은 문제를 줄일 구조와 작업 순서를 얻는다.

### 고급 독자

- 근거의 범위, 미확인 영역, 환경 차이, 재현 조건을 확인할 수 있다.
- 단순 재시도나 검사 추가가 아니라 원인 수정과 재발 방지 기준을 평가할 수 있다.

독자를 초보자라고 해서 기술적 사실을 단순화해 왜곡하지 않는다. 고급자를 위해 초보자의 흐름을 깨는 긴 세부사항은 본문 후반, 접힌 참고 영역, 별도 후속 글로 보낸다.

## 5. 근거 등급과 사실 규칙

### A. 실행으로 확인한 사실

실제 화면, API 응답, 파일, 테스트 결과, 로그, 배포 결과, 발행 URL처럼 지금 확인 가능한 자료다. 가장 강한 근거다.

### B. 당시 기록으로 확인한 사실

Git 이력, 세션 기록, 오류 로그, 작업 문서, 날짜가 남은 산출물처럼 사건 당시의 자료다.

### C. 작성자가 제공한 1차 경험

운영자가 직접 작성한 회고와 설명이다. 개인적인 판단과 감정의 근거로 사용할 수 있지만, 기술 원인까지 자동으로 확정하지 않는다.

### D. 외부 공식 자료

공식 문서, 제품 문서, 저장소 코드, 모델 카드다. 현재 상태가 바뀔 수 있는 내용은 발행 직전에 다시 확인한다.

### E. 추론과 미확인

가능성이 있는 설명이지만 증명되지 않은 내용이다. 사실 문장으로 바꾸지 않는다. 필요하면 “가능한 원인”, “다음에 확인할 항목”으로 명확히 표시한다.

서로 다른 기록이 충돌하면 더 강한 근거를 우선한다. 원본이 없으면 빈칸으로 남긴다. 그럴듯한 로그 문구, 날짜, 숫자, 화면을 새로 만들어 증거처럼 보여 주지 않는다.

## 6. 사건 선정 우선순위

1. 문제, 수정, 실제 결과가 모두 확인된 해결 사건
2. 일부가 해결됐고 남은 한계가 정확히 구분되는 사건
3. 해결되지 않았지만 초보자가 배울 진단 방법이 분명한 사건
4. 단순 기능 소개가 아니라 선택과 결과 사이에 의미 있는 변화가 있었던 구현 사건
5. 실제 비용, 시간, 품질, 운영 부담을 비교할 수 있는 실험

초기 편성 목표는 실제 근거가 있는 30편이다. 30이라는 숫자는 조사 범위와 운영 준비도를 확인하기 위한 목표이지, 근거가 부족한 글을 발행하는 할당량이 아니다. 비슷한 사건은 합치고, 근거가 약한 후보는 더 강한 사건으로 교체한다.

다음은 글로 억지로 분리하지 않는다.

- 원인과 교훈이 사실상 같은 작은 오류 여러 개
- 기록이 한두 문장뿐이고 결과를 확인할 수 없는 사건
- 제품 홍보 설명만 있고 개발 판단이나 검증이 없는 내용
- 검색량이나 발행 수를 채우기 위해 만든 가상의 경험

해결 사건을 우선하지만, 미해결 사건을 숨기지는 않는다. 미해결 글에는 두 영역을 분리한다.

- 실제로 확인된 사건 기록
- 개발자라면 다음에 어떤 순서로 확인할지에 대한 일반 진단 가이드

두 번째 영역을 과거에 실제로 수행한 것처럼 쓰지 않는다.

## 7. 글의 형태

모든 글을 같은 템플릿으로 만들지 않는다. 사건에 맞춰 다음 중 하나를 고른다.

- 개발 회고
- 문제 해결기
- 미해결 사건과 진단 지도
- 실험 보고서
- 실제 비용·시간 분석
- 구현 사례
- 도구 또는 접근법 비교
- 장기 프로젝트 연재
- 초보자용 개념 수업

형식은 달라도 기술 사건 글에는 다음 질문의 답이 있어야 한다.

1. 당시 무엇을 만들려 했는가?
2. 왜 그 선택을 했는가?
3. 기대와 실제가 어디에서 달라졌는가?
4. 무엇을 직접 확인했는가?
5. 무엇을 바꾸었는가?
6. 결과는 어떤 증거로 확인했는가?
7. 아직 모르는 것은 무엇인가?
8. 독자는 다음에 무엇을 다르게 할 수 있는가?

## 8. 분량과 문장 기준

기술 사건 원고는 본문 기준 3,000자 미만이면 짧은 이유가 분명해야 한다. 일반적인 목표 범위는 4,000~7,000자다. 분량을 맞추려고 같은 교훈을 반복하거나 일반론을 붙이지 않는다.

- 첫 20% 안에 사건과 핵심 문제를 보여 준다.
- 한 문단은 한 생각만 다룬다.
- 제목과 소제목은 추상적인 구호보다 독자의 실제 질문을 사용한다.
- “혁신적”, “완벽”, “압도적”, “성공” 같은 평가는 증거 없이 쓰지 않는다.
- AI 특유의 대칭 문장, 같은 길이의 항목 반복, 결론 재진술을 줄인다.
- 작성자가 일부러 남긴 솔직한 감정과 불편한 경험을 임의로 삭제하지 않는다. 개인정보와 법적 위험만 별도로 검토한다.
- 코드와 전문용어는 자랑하기 위해 넣지 않는다. 문제 이해나 재현에 필요한 부분만 보여 준다.

## 9. 교육 구조

글은 사건 기록에서 끝나지 않고 독자가 사용할 수 있는 지식으로 바뀌어야 한다.

- 사건 직후 “왜 이런 일이 생길 수 있는가”를 쉬운 말로 설명한다.
- 비슷해 보이지만 다른 개념을 구분한다. 예: 코드 작성 / 단위 검증 / 통합 검증 / 실제 사용 검증.
- 잘못된 질문과 더 나은 질문을 함께 보여 준다.
- 독자가 AI에게 그대로 요청할 수 있는 검증 문장이나 체크리스트를 제공한다.
- 해결책은 당시 실제로 한 조치와, 지금 권하는 일반 원칙을 구분한다.
- 글 끝에는 다음 단계 또는 관련 글을 연결한다.

개발자 노트 전체는 결과적으로 바이브 코딩 교재처럼 읽혀야 한다. 초급 글에서 용어와 확인 습관을 익히고, 중급 글에서 구조와 연결을 배우며, 고급 글에서 운영·관측·보안·비용·재발 방지를 다룬다.

## 10. 시각 편집 기준

시각 자료는 장식이 아니라 이해를 줄이는 도구다. 기술 사건 글은 원칙적으로 다음 세 종류를 검토한다.

1. 증거 자료: 실제 화면, 비식별 로그, 결과 파일, 전후 비교
2. 설명 자료: 구조도, 흐름도, 단계 비교, 원인과 결과의 관계
3. 실행 자료: 체크리스트, 판단 카드, 복사 가능한 질문, 검증 순서

모든 글에 억지로 정확히 세 장을 넣지는 않는다. 하지만 긴 기술 글이 텍스트만 이어진다면 시각 설계를 다시 검토한다.

### 외형

- OMNIARK의 다크 스튜디오 배경을 유지한다.
- 순검정 카드가 끝없이 반복되는 화면은 피한다.
- 청록, 파랑, 보라, 주황 등은 의미가 다른 상태와 구역을 구분할 때 사용한다.
- 본문은 눈부신 순백이 아니라 따뜻한 밝은 회색을 사용한다.
- 고급 개발 도구처럼 정밀하되, HUD 선·격자·광원·장식 문자를 과하게 쌓지 않는다.
- 박스가 둥둥 떠다니는 반복 애니메이션은 사용하지 않는다.
- 모션은 단계 전환, 데이터 흐름, 원인과 결과처럼 움직여야 이해되는 경우에만 쓴다.
- `prefers-reduced-motion`에서 모든 비필수 모션이 멈춰야 한다.
- 모바일 390px에서도 글자와 도식이 읽히고 가로 스크롤이 없어야 한다.

### 증거 이미지

- 원본 스크린샷이 없으면 재구성본을 실제 화면처럼 속이지 않는다.
- 재구성본에는 “기록을 바탕으로 재구성”, “식별정보 제거” 같은 표기를 넣는다.
- API 키, 계정, 개인 경로, 세션 ID, 내부 사업 수치, 원문 전체 로그는 가린다.
- 가린 부분 때문에 핵심 문구까지 읽을 수 없게 만들지 않는다.
- 모든 이미지에 내용이 드러나는 대체 텍스트를 작성한다.

기존 제미나이 작성 게시물은 내용의 사실 근거로 사용하지 않는다. 다만 사용자가 좋다고 판단한 레이아웃, 정보 위계, 카드 구성, 개발자 화면의 분위기, 요소별 모션은 시각 레퍼런스로 분석할 수 있다. 좋은 외형을 재사용할 때도 현재 글의 실제 의미와 근거에 맞게 다시 설계한다.

## 11. 검색·답변형 AI 구조

검색 최적화는 사실이 풍부한 글을 발견하기 쉽게 만드는 작업이다. 빈 글을 길게 만들거나 키워드를 반복하는 작업이 아니다.

- 제목은 사람이 실제로 묻는 한 가지 문제를 분명히 드러낸다.
- 도입부에서 사건과 답의 범위를 먼저 말한다.
- H2는 질문, 원인, 해결, 검증처럼 독립적으로 이해되는 문장으로 쓴다.
- 어려운 개념은 짧은 정의 문장을 둔다.
- 사건 시점, 작성일, 수정일, 확인 범위를 관리한다.
- 관련 개발자 노트 2~4편을 문맥 안에서 연결한다.
- FAQ는 실제로 본문에서 답한 질문이 있을 때만 만든다.
- 메타 설명은 글의 사건·독자·얻을 수 있는 답을 한 문단으로 요약한다.
- 구조화 데이터는 사이트의 공용 구현을 사용한다. 원고에 임의 JSON-LD를 삽입하지 않는다.
- 출처가 필요한 외부 기술 사실은 가능한 한 공식 자료에 연결한다.
- SEO, AEO, GEO를 이유로 확인되지 않은 전문성·경험·성과를 만들지 않는다.

## 12. 상태와 작업 흐름

한 편은 다음 순서를 따른다.

1. 후보: 사건의 제목과 자료 위치만 등록
2. 조사 중: 기록을 모으고 사실과 불확실성을 분리
3. 사건 카드: 시점, 목표, 문제, 변경, 결과, 근거, 민감도를 정리
4. 편집 초안: 독자 서사와 기술 설명 작성
5. 시각 제작: 근거와 주장에 맞는 자료 제작
6. 사실 검수: 문장별 근거, 개인정보, 과장, 미확인 확인
7. Studio 초안: `app/content/drafts`에 `status: draft`로 가져오기
8. 화면 검수: 실제 데스크톱·모바일 렌더, 이미지, 대체 텍스트, 링크 확인
9. 발행 대기: 운영자 검토가 가능한 상태
10. 발행: 명시적 승인 뒤 한 편만 공개 전환
11. 업데이트: 새로운 검증 결과가 생기면 수정일과 변경 이유 기록

단계를 건너뛰어도 되는 것은 오탈자 같은 작은 수정뿐이다. 기록이 없는 글을 바로 발행 대기로 올리지 않는다.

## 13. Studio 편집기 원칙

Omniark Studio는 완성된 JSON을 바라보기만 하는 목록이 아니라, 운영자가 글과 시각 요소를 직접 다듬을 수 있는 편집 공간으로 발전시킨다. 노션을 겉모습만 흉내내지 않고 다음 작업 흐름을 기준으로 삼는다.

- 제목, 본문, 소제목, 인용, 코드, 목록, 체크리스트, 구분선, 이미지, 캡션, 콜아웃, 표를 블록 단위로 편집한다.
- 블록을 추가, 삭제, 복제, 이동할 수 있고 키보드 작업이 끊기지 않아야 한다.
- 개발 지식이 없어도 색조, 강조 수준, 이미지 위치, 캡션, 관련 글을 조정할 수 있어야 한다.
- 자유로운 꾸미기를 허용하되 사이트를 깨뜨리는 임의 HTML·스크립트·CSS는 저장하지 않는다.
- 증거, 설명, 체크리스트처럼 의미가 있는 시각 블록을 제공한다. 단순한 장식 박스를 늘리지 않는다.
- 데스크톱과 모바일 미리보기를 편집 중에 확인할 수 있어야 한다.
- 저장과 발행을 분리한다. 저장은 항상 초안이며, 발행은 별도 확인을 거친 명시적 동작이다.
- 원고 최초 작성일, 실제 사건 시점, 최근 수정일, 근거 상태, 변경 이력을 보존한다.
- 이미지 업로드 시 대체 텍스트와 캡션을 함께 편집하고, 민감정보 확인을 거치게 한다.
- 기존 Markdown 원고와 안전한 블록 형식을 잃지 않고 가져오거나 내보낼 수 있어야 한다.

편집기 고도화는 실제 작성 중 막힌 기능부터 진행한다. 노션의 모든 기능을 한 번에 복제하는 프로젝트로 확장하지 않는다.

## 14. CMS와 파일 경계

- `app/content/drafts`: Omniark Studio의 비공개 검토용 원고
- `app/content/posts`: 공개 사이트가 읽는 게시물
- `public/images`: 공개 또는 초안 렌더링에 쓰는 시각 자산

초안 가져오기는 기존 Revenue Forge 도구를 사용하고 `--only`로 한 편만 갱신한다. 전체 폴더 재가져오기로 편집자가 고친 다른 초안을 덮어쓰지 않는다.

초안 파일이 만들어졌다는 사실은 발행이 아니다. 공개 게시물 전환, 배포, 검색 색인 요청은 각각 별도의 상태 변화다.

## 15. 반드시 승인이 필요한 작업

- 새 글 공개 발행
- 기존 공개 글의 내용·슬러그·제목·발행일 변경
- 공개 글 삭제 또는 비공개 전환
- 예약 발행 또는 자동 발행 활성화
- 사이트 전체 배포
- 대량 초안 덮어쓰기
- 공개되지 않은 사업 정보나 개인 정보 포함

조사, 사건 카드, 원고 작성, 시각 자료 제작, 비공개 Studio 초안 추가, 테스트와 로컬 검수는 승인 없이 진행할 수 있다.

## 16. 한 편의 완료 조건

다음 항목이 모두 확인돼야 “발행 대기 완료”라고 보고한다.

- 사건 카드 1개 이상이 있고 실제 근거 위치가 연결돼 있다.
- 핵심 주장마다 확인 상태가 구분돼 있다.
- 해결됐다는 문장은 실제 결과로 검증됐다.
- 미확인 원인과 남은 문제를 숨기지 않았다.
- 초급 독자가 이해할 설명과 바로 쓸 확인 방법이 있다.
- 의미 있는 시각 자료가 들어갔거나, 넣지 않은 이유가 기록돼 있다.
- 이미지 대체 텍스트와 모바일 가독성을 확인했다.
- 내부 경로, 키, 계정, 세션 ID, 개인정보 노출이 0건이다.
- 제목, 설명, 소제목, 관련 글 연결이 준비됐다.
- Studio 데이터가 실제로 `status: draft`다.
- 렌더러·가져오기·관련 빌드 테스트가 통과했다.
- 공개 글과 예약·배포 상태는 바뀌지 않았다.

“작성 완료”와 “발행 완료”를 같은 말로 쓰지 않는다.

## 17. 작업 보고 형식

최종 보고에는 세 가지만 분명히 적는다.

### 한 것

실제 파일, 테스트 수, 초안 상태, 화면 또는 URL처럼 확인 가능한 결과를 적는다.

### 못 한 것과 이유

근거 부족, 외부 로그인, 원본 부재, 승인 대기처럼 실제 경계를 적는다. 숨기거나 성공으로 바꾸지 않는다.

### 다음 한 수

사용자가 판단해야 하는 한 가지가 있으면 쉬운 말로 말한다. 판단이 필요하지 않으면 다음 초안 작업을 계속한다.

## 18. 기준 변경

새로운 합의가 생기면 세션 기억에만 두지 않는다. 이 문서를 같은 작업 안에서 갱신한다. 작업 방식의 짧은 강제 규칙이 바뀌면 루트 `AGENTS.md`도 함께 갱신한다.

세부 디자인 토큰, 렌더러 문법, 검색 구현처럼 코드와 함께 변하는 내용은 각각의 구현 문서에 둔다. 이 문서는 목적, 품질, 사실, 승인 경계를 관리한다.

## 19. 참고한 외부 구조

- [OpenAI Codex Prompting Guide](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide): 폴더별 `AGENTS.md`가 작업 맥락에 자동으로 합쳐지는 구조
- [AGENTS.md Specification v3.0](https://github.com/TechSpokes/agency-specifications-files-agents-md/blob/main/SPECIFICATION.md): 짧은 강제 규칙과 상세 문서를 분리하고, 중요한 규칙을 앞에 두는 방식
- [Diátaxis](https://www.diataxis.fr/): 튜토리얼, 방법 안내, 참고자료, 개념 설명을 독자의 필요에 따라 구분하는 기술 문서 구조

## 20. 검색 수요와 답변형 AI 발견 원칙

글감은 항상 실제 개발 사건에서 시작한다. 그 뒤에만 독자의 질문, 검색 의도, 관련 검색어, 경쟁 결과의 빈틈을 조사한다. 검색량이 높다는 이유로 근거 없는 주제를 먼저 만들거나, 실제 한 사건을 여러 개의 유사 글로 쪼개지 않는다.

- 검색량·경쟁도·추세는 확인 가능한 도구와 확인 날짜를 함께 기록한다. 조회할 수 없는 숫자는 비워 둔다.
- 제목과 H2는 실제로 답하는 질문을 드러내되, 키워드를 반복 삽입하지 않는다.
- 기술 비교·문제 해결 글은 질문, 답의 범위, 측정 조건, 결과, 한계, 업데이트 시점을 분명히 한다.
- FAQ는 본문에서 실제로 답한 질문이 모였을 때만 사용한다. 답이 없는 FAQ나 임의의 Q&A 구조화 데이터는 만들지 않는다.
- 검색용 크롤러와 모델 학습용 크롤러의 정책은 별개다. `robots.txt`, `llms.txt` 또는 특정 봇 허용 여부가 인용을 보장한다고 주장하지 않으며, 크롤러 정책 변경은 운영자 공개 범위의 결정이다.
- 공개 경로·canonical·응답 코드·서버가 읽을 수 있는 본문·사이트맵·robots·메타데이터·구조화 데이터·모바일 가독성·내부 연결은 실제 배포본에서 점검한다.

세부 조사 순서, 기술 점검 항목, 측정 계획은 `DEVELOPER_NOTES_GROWTH_SYSTEM.md`를 따른다.

## 21. 모델 비교와 비용 글의 검증 경계

모델·추론 수준·사용량·가격·한도는 시간에 따라 달라진다. 이를 다루는 글은 운영자의 사용 감상과 비교 실험 결과를 구분한다.

- 공식 문서의 모델명·지원 설정·가격·한도는 확인 날짜와 함께 기록한다.
- 비교 실험은 같은 시작 상태, 지시문, 도구 권한, 완료 조건을 가능한 한 동일하게 맞춘다.
- 운영 중인 프로젝트가 아닌 격리된 복제 환경에서 수행하고, 단일 사례를 일반적 우열로 단정하지 않는다.
- 완료 여부, 테스트, 실제 사용 가능성, 재시도 횟수, 시간, 토큰 또는 확인 가능한 비용을 각각 기록한다.
- 실측이 없는 평가는 경험적 의견으로 표시한다.

## 22. 발행 뒤의 개선과 애드센스 경계

발행은 끝이 아니라 검증 가능한 학습의 시작이다. Google Search Console, 네이버 도구, 분석 도구, 서버 로그처럼 실제로 접근 가능한 자료로 노출·클릭·검색어·내부 이동·제품 연결을 확인한다. AI 추천·인용·방문 출처는 완전히 측정할 수 없음을 전제로 하며, 확인된 UTM 등만 근거로 쓴다.

애드센스 재심사는 글 수를 채우는 일이 아니다. 원본 경험, 사이트 탐색성, 완성된 공개 페이지, 정책·개인정보·연락 경로, 모바일 접근성, 제품의 공개 상태를 함께 점검한다. 승인 여부는 운영자가 결정하며, 실제 계정 상태가 확인되기 전까지 성공으로 보고하지 않는다. 현재 계정 관련 사실은 `ADSENSE_STATUS.md`를 우선한다.

## 23. 기존 시스템 재사용과 자율 운영의 경계

Revenue Forge, One Pass Cut, Omniark Local MCP, 기존 Work 영상 제작·예약 발행, 서비스 저장소와 제작 자산은 먼저 조사해 재사용한다. 새 공장은 기존 시스템이 명확히 해결하지 못하는 마찰과 유지보수 비용이 확인된 뒤에만 제안한다.

Work는 자료 조사, 사건 카드, 초안, 시각 자료, 검증, 발행 준비를 자율적으로 수행할 수 있다. 그러나 자동 공개, 예약 발행 활성화, 기존 공개 글 교체, 사이트 구조 변경, 외부 계정 설정 변경은 이 문서의 승인 경계를 그대로 따른다.

## 24. 사건 카드의 확장 필드

사건 카드에는 기본 근거 외에 다음을 함께 관리한다.

- 프로젝트, 사건 시점, 당시 목표, 문제, 선택, 시도, 검증 결과, 해결 상태
- 원본 파일·Git·로그·화면의 위치와 민감정보 위험
- 독자가 얻을 개발 지식, 실제로 답할 질문, 관련 검색 의도
- 후속 글 가능성, 관련 글 연결, 모델·제품 정보의 확인 날짜
- 공개 후 관찰할 지표와 업데이트가 필요한 조건

## 25. 수익화의 현실과 자격 조건

수익화는 개발자 노트의 중요한 주제지만, 자동화·AI·콘텐츠 제작이 곧바로 수익이 된다는 서사로 다루지 않는다. 광고, 제휴, 소프트웨어 판매, 유료 서비스, 디지털 상품, 컨설팅·제작 의뢰 등 어떤 경로든 실제로 통과해야 하는 조건을 먼저 밝힌다.

- 플랫폼 가입·심사·연령·지역·사업자·세금·지급 수단 같은 자격 요건
- 콘텐츠 또는 제품 품질, 정책 준수, 저작권·라이선스, 개인정보·광고 표시 의무
- 발견 가능성, 신뢰, 유입, 전환, 유지, 고객 지원, 환불·정산, 운영 비용
- 실험의 기간, 투자한 시간·도구 비용, 확인된 결과, 미확인 결과와 손익분기 전 상태

각 글은 ‘가능한 수익 경로’, ‘확인된 운영 조건’, ‘OMNIARK가 실제로 시도한 범위’, ‘아직 통과하지 못했거나 검증하지 못한 조건’을 분리한다. 정책·자격·세금·수수료처럼 변할 수 있는 사실은 해당 서비스의 공식 자료와 확인 날짜를 남기며, 개인별 법률·세무 판단처럼 전문 확인이 필요한 영역을 단정하지 않는다.
